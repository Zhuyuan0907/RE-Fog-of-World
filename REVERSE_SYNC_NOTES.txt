What is already established
- Android Java/smali layer is not the core exploration engine. The core lives in libapp-jni.so.
- Native symbols clearly include:
  - fogofworld::ExplorationDocument
  - fogofworld::StatisticDocument
  - ExplorationDocument::GetExplorationStates(...)
- ConvertMapPointToDocument was disassembled and the grid math is now known:
  - internal world pixel space is effectively Web Mercator around z20
  - divide by 64 => exploration cell grid
  - document size = 8192 x 8192 cells
  - block size = 64 x 64 cells
  - blocks per document = 128 x 128
  - blockId = blockX + blockY * 128
  - documentId = documentX + documentY * 512

Sync format findings
- The 9 files in /Users/zhuyuanjiang/Downloads/Sync are zlib-compressed binary files.
- After decompression, they are not raw polylines and not a single row-major bitmap.
- Current highest-confidence structure:
  - first 128 pages are the root index
  - page size = 256 bytes
  - root index = 128 x 128 uint16 references
  - each non-zero reference points to 2 payload pages
  - each payload page decodes as 64 x 32 bits
  - two payload pages together form a 64 x 64 explored block
- This means Sync is much closer to explored-state block storage than GPS route storage.

Why the current web result is "partly right"
- The leaf block bitmap content is now being decoded from the root/leaf page tree.
- That is why the imported Sync no longer looks like horizontal noise.
- The main remaining error is document classification / placement:
  - which decompressed file corresponds to W / AS / AF / NA / SA / AN / EU / OC
  - and whether any trailing pages contain metadata to make that mapping exact
